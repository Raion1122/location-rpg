# 開発会議（位置RPG Dev Meeting）

「位置RPG」の次の一手を、4 人の専門家エージェントが議論して決めるための仮想開発会議スキル。会議は**2 段階**で進行する。各エージェントの**対話ログ**を再現したうえで、慶彦さん（プロジェクトオーナー）が決断できる形に落とす。

> ダンジョンファイターズの `dev-meeting` を元に、位置RPG 用に書き換えたもの（2026-09-15）。
> ⛔ **ダンジョンファイターズ側のスキル・ファイルは読みに行かない**（位置RPG はダンジョンファイターズとコードでつながない方針）。

## 会議の 2 段階構造（最重要）

このスキルは必ず以下の 2 段階で進む。**第1段で勝手に第2段へ進まない。** 第1段の提案を出したら一度止まり、慶彦さんの選択を待つ。

- **第1段：発散会議（候補出し）**
  ジャンルの違う実装候補を複数（推奨 3〜4 個）出し合って議論し、提示する。肝は「毛色の違う方向性」を並べること（似た案を 3 つ出さない）。慶彦さんはこの中から 1 つ選ぶ。
- **第2段：収束会議（実装計画）**
  慶彦さんが選んだ 1 案について、実装に向けて再度議論し、**開発計画書**を作成する。

## このスキルのゴール

1. 議題に対して 4 人がキャラクターを保ったまま議論する（対話ログ重視）
2. 対立・妥協・発展を含む生きた議論にする（全員賛成の予定調和を避ける）
3. 第1段でジャンルの異なる候補を複数提示し、慶彦さんが選べる状態にする
4. 第2段で選択案を開発計画書に落とし込み、そのまま実装に入れる粒度にする

## 開催フロー

## 第1段：発散会議（候補出し）

### 1-0. 会議の前に本番のファイルを測る（必須）

測らずに会議を開くと、発言や計画書に「もう無い仕組み」「実は済んでいる仕事」が紛れ込む。会議の前に次を読む。

- `README.md`（今の遊び方・ファイルの役割）
- 議題に関わる本番のファイル: テスト用ゲームの画面 `demo-game.html` / 地図ツール `map.html` / 戦闘のルール `dungeon.js` / クエストのルール `quest.js` / 中継サーバー `server.js` / 位置の差し替え `fake-gps.js` / 置いたものの保存 `dungeons.json`
- `dev-meetings/` の直前の会議記録。とくに「作らないもの」「次回議題」（次の題材が既に決まっていることがある）
- メモリに残っている「提案して未回答」の項目（議題の候補になる）

エージェントに言わせる数字・関数名・ファイル名は、ここで Grep して**実在を確かめたもの**だけを使う。

### 1-1. 議題の確定

- ユーザーの相談内容を 1〜2 行の議題に言語化し、冒頭で提示する。
- 議題が曖昧なら、勝手に決めず確認質問を 1 つだけする。選択肢を出すときは「第2段の会議で決めたい」も混ぜる（決められない問いで会議が止まらない）。

### 1-2. 制約のリマインド（毎回内部で確認）

会議の全発言は以下の不可侵制約を守る。違反案は ノエル（QA/UX）か レンツ（システム）が必ず指摘して潰す。

- **安全第一**: 車道・線路・踏切・駅のホーム・他人の敷地・立入禁止の場所にダンジョンやクエスト主を置かせない。画面を見続けないと進まない作り・走らせる作り・夜中や危ない場所へ誘う作りにしない。
- **スマホのブラウザで遊ぶ（iPhone Safari 最優先）**: アプリストアは使わない。本物の位置情報は HTTPS でしか取れない（自宅 LAN の http で動いているのは疑似 GPS に差し替えているから）。ブラウザは画面を閉じると位置を取れないので、バックグラウンドでの追跡や歩数を前提にしない。音を足すなら mp3・AudioContext はタップで解除・事前ロード。
- **GPS はブレる**: ±10m は揺れる前提。ブレで戦闘が切れる・向きがくるくる回る・範囲の出入りを繰り返す作りにしない（今のゲームは、戦闘中に範囲外へ出ても追い出さない）。
- **歩かずに試せること**: 新しい仕組みは、地図ツールのピン（疑似 GPS）で現地に行かずに確かめられる形にする。確かめ方は `tools/verify_map_tool.js` に項目を足し、`node tools/verify_map_tool.js` で回す。
- **疑似 GPS は自作ゲームの中だけ**: 差し替えが効くのは localhost と自宅 LAN だけで、公開ホストでは効かない。この線引きを崩さない。ほかの位置ゲーの位置をごまかす案・チート検知を避ける案は出さない。
- **ダンジョンファイターズとはコードでつながない**: 流用してよいのは絵だけ（`sprites/` にコピーしてから使う）。あちらのフォルダを直接読みに行く案、コードやデータを共有する案は出さない。
- **Product Identity 除外**: D&D 風の戦い（d20）だが、Beholder・Mind Flayer・Displacer Beast など WotC 固有の IP は使わない。
- **今ある仕組みの使い回しが最優先**: 新しい案は、まず次の流用で済まないかを考える。データの行を足すだけで済ませる。
  - 敵とダンジョンの顔ぶれ = `dungeon.js` の `MONSTERS` / `LINEUPS`（画面のファイルは触らなくてよい）
  - 依頼の言葉・報酬・クエスト主の見た目 = `quest.js` の `REQUESTS` / `LOOKS`
  - 置く・飛ぶ・保存 = 地図ツール `map.html` と `dungeons.json`（`server.js` の `/gps/dungeons`）
  - 冒険者と依頼の進み具合 = その端末の localStorage（`locgame.hero.v1` / `locgame.quests.v1`）。サーバーには送らない
- **複数ファイルに同じものを足す所**: 変更案はこの手間に必ず触れる。
  - ダンジョンの種類 = 絵 `sprites/dungeon/<kind>.png` ＋ `demo-game.html` の `KIND_EMOJI` ＋ `map.html` の `KINDS` の 3 か所
  - 自分（戦士）の絵 = `demo-game.html` と `map.html` の CSS `.npc.hero`
- **サーバーは Node 標準だけ**: `server.js` は追加インストール無しで動く。`server.js` を変えたら、動いているサーバーを止めて起動し直す必要がある（起動用の vbs では古いサーバーが残る）。**全員で同じ敵を共有する（倒したら消える・レイド）などは、サーバー＋データベースが要る大仕事**として扱う。
- **地図**: タイルは OpenStreetMap（API キー不要・開発と少人数向け）。公開して多くの人が遊ぶ段になったらタイル配信の切り替えが要る。CARTO はキー無しだと透かしが出るので使わない。
- **日本語コンテンツ**: ゲーム内テキストは全て日本語。
- **素材調達のルール（重要運用ルール）**: 外部素材の調達を伴う案は、次のどれかに収まること。
  - **(a) 自動取得ルート**: スクリプトで URL 取得できる素材は、エージェントが自動 DL まで段取りする。慶彦さんは採否を決めるだけ。例: 魔王魂（maou.audio）、Kenney CC0 パック、ユーフルカ（Wingless Seraph）。
  - **(b) 手動取得ルート**: 利用規約上スクリプト化できない素材（例: 効果音ラボ、OtoLogic）も**提案してよい**。ただし**具体的なダウンロード URL（または対象ページ URL ＋ DL 手順）まで示す**。「素材サイトで探して」の丸投げは禁止。
  - **(c) 描かせるルート（Codex）**: 絵は Codex に描かせてよい（2026-09-14 のダンジョンの入口 6 種が前例。依頼文 `Desktop\codex1\requests\2026-09-14_dungeon-entrance-sprites.md` を型にする）。**依頼文を起草 → 慶彦さんの承認 → 投下** の順を守る。依頼文には「⛔ プロセスを止めない / 一時ファイルは消さずに残す」を必ず書く（前回 Codex が PowerShell ごと強制終了した）。納品物は `sprites/` へコピーして使う。
  - **(d) 絶対回避**: **アカウント登録（サインアップ）が必要なサイトは使わない。** 有料素材・ログイン必須サイトも除外。
  - レンツが素材源ごとに「自動 DL 可 / 手動だが URL 直指定可 / Codex に描かせる / 登録必須で NG」を必ず判定する。登録必須の素材源が出たら却下し、代替に差し替える。
- **慶彦さんは決裁者（手作業は最小限）**: 原則「エージェントが取得まで設計し、慶彦さんは採否を決めるだけ」。慶彦さんに確かめてもらう操作は、**どの画面（地図ツール / テスト用ゲーム、PC / スマホ）の、どこの、何ボタンか**まで書く。

### 1-3. 発散議論（対話ログ）

`references/agents.md` の 4 人のペルソナを読み込み、各エージェントとして発言する。第1段の目的は**ジャンルの違う候補を広げること**。深掘りより方向性の幅を優先する。

- **第1ラウンド（ブレスト）**: チーフが議題を枠付け → 各人が**自分の専門領域から 1 つずつ**毛色の違う方向性を出す。例: ガイウス = 冒険の中身（依頼・ダンジョン・物語）、レンツ = 仕組み（戦闘・成長・装備・保存・サーバー）、ミサキ = 地図と見た目（人形・入口の絵・演出）、ノエル = 歩きやすさ・手触り・安全。これで自然にジャンルが散る。
- **第2ラウンド（絞り込み）**: 出た方向性のうち、制約をクリアできないもの・使い回しが効かず重すぎるものをノエルとレンツが間引く。残った中から候補を 3〜4 個に整理。
- 各発言は **【名前】** ラベル付き。1 発言は 2〜5 文程度でテンポよく。
- 1-0 で測った事実は発言に使ってよい。実測で意見を変えるエージェントは、会議を予定調和にしない。
- この段階では 1 案を深掘りしすぎない（深掘りは第2段の仕事）。

### 1-4. 候補の提示と一時停止

`references/output-format.md` の「第1段」テンプレートに沿って候補を提示する。

- **ジャンルの異なる候補を 3〜4 個**。各案に「ジャンル／狙い／ざっくり規模／使い回し度／歩かずに試せるか／スマホ・安全／推し・慎重」を簡潔に付す。
- 詳細（細かい工数やリスク）は第2段で詰めるので、ここでは深入りしない。
- 最後に必ず「**どの方向性を進めますか？**」で止め、慶彦さんの選択を待つ。**勝手に第2段へ進まない。**

---

## 第2段：収束会議（実装計画）

慶彦さんが第1段の候補から 1 つ選んだら、この段に進む。

### 2-1. 選択案の確認

- 選ばれた案を 1〜2 行で再提示し、「この方向で実装会議を始めます」と宣言する。

### 2-2. 実装議論（対話ログ）

選択案 1 本に絞り、実装に向けて深掘りする。

- **第1ラウンド（設計）**: レンツが、どのファイルのどの仕組みを使い回し、何を新しく作るかを示す。複数ファイルに足す所・保存の形（`dungeons.json` の項目 / localStorage のキー）・サーバーの起動し直しが要るかも、ここで洗う。
  ⭐ **第1段で出た案は、本番の関数に当ててから信じる。** 案が動いても、確かめたいものがその経路を実際に通るとは限らない。
- **第2ラウンド（肉付けと衝突）**: ミサキが地図の見た目と絵を、ガイウスが冒険の組み立てを、ノエルがスマホ実機で歩きながらの手触り・GPS のブレ・安全・エッジケースを詰める。最低 1 つは健全な対立を起こし、折衷で着地させる。
- **第3ラウンド（合意）**: 実装順序・フェーズ分割・素材調達の段取り・歩かずに確かめる手順を確定する。
  ⭐ **第1段で「第2段で決める」とした判断は、ここで実データを出して必ず決着させる。** 両睨みのまま計画書にしない。

### 2-3. 開発計画書の作成

`references/output-format.md` の「第2段」テンプレート（開発計画書）に沿って出力する。

- フェーズ単位で完結する実装ステップ、使い回す仕組み、新規実装、触るファイル、保存するデータ、素材調達、歩かずに確かめる手順と検証に足す項目、スマホ実機と安全の確認、リスクと対策を網羅する。
- 末尾で引き継ぎ先（2-4）を示す。

### 2-4. 引き継ぎ

開発計画書を出したら会議は終了。**実装そのものはこのスキルの範囲外。** 慶彦さんの修正・承認を待ち、次のどちらかへ進む。

- **この窓でそのまま実装する**（会議で読んだファイルが context に残っているので早い）
- **窓更新して、新しい窓で実装する**（`window-refresh` で ⚓アンカーに会議記録のパスを残す。会議が長くなったときはこちら）

実装に入るときは、計画書の主張をもう一度本番のファイルで確かめる（会議から時間が経つとずれる）。

## 会議記録の保存（見返し用・必須）

会議の出力は、その都度プロジェクト直下の `dev-meetings/` フォルダに保存し、後から見返せるようにする。

- **1 議題 = 1 ファイル**。命名は `dev-meetings/YYYY-MM-DD_<議題の短いslug>.md`。
- **第1段**を出したら、対話ログ＋候補一覧をそのファイルに保存する。
- **第2段**の開発計画書は、**同じファイルに追記**する（第1段の下に続ける）。「候補 → 決定 → 計画書」が 1 ファイルで追える。
- 会議のあとで前提が崩れたと分かったら、候補を黙って差し替えず、冒頭に「会議後に判明したこと」の節を立てて経緯ごと残す。
- 決定は記号だけで書かない（「③」ではなく「候補③ ○○」まで書く）。
- チャット表示と保存内容は同一でよい。保存したら保存先パスを一言添える。
- 詳しい運用は `dev-meetings/README.md` を参照。

## エージェント構成（詳細は references/agents.md）

| 役 | 名前 | 担当 | 口癖・視点 |
|---|---|---|---|
| チーフ／シナリオ | ガイウス | D&D らしさ、クエストの組み立て、実際の街を冒険の舞台として読む | 「これは D&D か？ 歩いた先に冒険はあるか？」 |

## 重要な作法

- **予定調和を避ける**: 4 人が全員賛成して終わる会議は失敗。必ず緊張を作る。
- **慶彦さんを「会議に出てくる開発者」ではなく決裁者として扱う**: エージェントは提案までが仕事。最終決定はしない。
- **過剰な持ち上げをしない**: 案の弱点を正直に指摘する。QA/UX 役は特に辛口でよい。
- **スコープ厳守**: 1 会議で扱う議題は 1 つに絞る。話が広がりすぎたら次回議題として切り出す。
- **2 段階を厳守**: 第1段（候補出し）で必ず止まり、慶彦さんの選択を待ってから第2段（開発計画書）へ進む。慶彦さんが最初から「この方向で計画書まで作って」と指定した場合のみ、第2段へ直行してよい。
- **測ってから話す**: 1-0 を飛ばさない。
- 詳細な出力テンプレートは `references/output-format.md` を参照。
